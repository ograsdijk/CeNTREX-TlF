# RC propagation acceleration implementation plan

**Superseded and deferred:** the [cross-system benchmark suite](RC_CROSS_SYSTEM_BENCHMARK_PLAN.md) now comes first. Revisit this production proposal only after that matrix is reviewed.

**Status: deferred pending cross-system results.** This proposal preserves the earlier SoA-promotion and photon-adjoint ideas for later review. It does not authorize production API changes or default changes. The current authorized work is the fixture and screening suite linked above; historical benchmark results stay in [the results report](rc_propagation_results/README.md).

## Evidence and decisions

The strongest broadly replicated result is the SoA structured sparse–dense RHS variant. In the completed 11-case detuning/power matrix it reduced paired wall time by 18.1–19.9% in ten cases, each with three accepted observations. The −100 MHz case has only two accepted observations at tighter tolerance. The earlier short nominal 10 µs case measured 5.417 s versus 6.678 s for the `structured` full-density-plus-separate-photon trajectory (18.9% lower). These results cover a 70-state system, 10 µs duration, 137 ns entry phase, and tested detuning/power combinations; they do not establish a 200 µs or production-workload win. See the [matrix summary](rc_propagation_results/rc_kernel_matrix_v1/nominal/case_summary.json).

The all-state adjoint study is narrower. In one nominal 1 µs case, a single photon adjoint returned responses for all 70 one-hot initial states in 7.155 s, compared with 37.932 s serial Rust, 14.929 s with three Rust threads, and 7.166 s with eight threads. It passed all-state comparison against the strict photon reference, with maximum absolute error `4.15e-11`. At K=20 its 7.155 s all-70 solve was slower than three- and eight-thread direct batches. The corresponding X J=1 adjoint also tied the eight-thread K=70 result within one percent. Each timing is a single observation. These measurements show an amortization opportunity against serial work at K=70, not an established throughput gain over parallel batches. An adjoint returns scalar responses, never final density matrices. Full-density callers continue to need a forward solver.

The package/global default is currently `expanded_sparse` with `dopri5`; the RC recommendation is `structured`. The implementation decision is to prepare a stable opt-in name, `structured_sparse_dense`, routing to the measured SoA native RHS. Leave both defaults and the RC recommendation unchanged until the longer validation gates below pass. Retain `experimental_structured_sparse_dense_soa` as a compatibility alias to that same implementation, without adding a deprecation warning initially. Preserve the existing `experimental_structured_sparse_dense`, diagonal-split, and single-unpack modes as distinct implementations with their measured semantics; do not silently redirect them to SoA. Do not combine diagonal split or single-unpack with SoA absent a measured ablation. Do not claim SIMD: the measured kernel separates real and imaginary scratch arithmetic while the input density remains interleaved complex.

Treat a native total-photon adjoint as a separate optional scalar-response API proposal, not a forward `execution_mode` and not an automatic replacement when a caller asks for photon output. The implementation path starts with an internal opt-in Rust engine and correctness tests; exposing a public API is a later performance/readiness gate, not a prerequisite to beginning the native prototype. A future public entry point could be a standalone `prepare_photon_response` / `photon_response_scan` interface; its final name and contract require review after the internal prototype. It should take an existing prepared problem, solver/tolerances, parameter overrides/batch and thread controls, and objective weights with the same meaning as `photon_integral`. It returns only each parameter point's response vector over basis-diagonal initial states at t0 plus solver statistics; it does not return an adjoint trajectory or density matrices. Diagonal initial mixtures are evaluated as a weighted dot product of that response vector. Do not imply support for arbitrary initial coherences, state-dependent feedback, nonlinear objectives, stopping events, sampled/full outputs, or full-density output. The first implementation target is the caller-specified weighted integral contract; for the RC photon case the weights are `Γ` on B-state populations. Terminal populations can be a later objective-specific extension.

## SoA promotion path

1. **Preserve the measured implementation and interface behavior.** Add the stable opt-in route to the existing SoA implementation with no duplicate kernel. Keep only the prior SoA spelling as its alias; preserve other experimental modes and spellings as distinct implementations. The package defaults remain `expanded_sparse` and `dopri5`, and `structured` remains the RC recommendation; no automatic workload-size or timing-based router is added. Document supported solvers, output modes, batch inputs, thread behavior, and fallback/error behavior from the real API.
2. **Run correctness and short convergence checks on the current native build.** Build independent current-native references for a nominal short case and a small representative set spanning detuning and optical power. Reuse an existing reference only when model, rates, configuration, source revision, native extension, solver settings, and saved outputs match exactly; otherwise create a fresh reference. Include full density matrices and coherences, photon integrals, total and selected populations, and verify trace, Hermiticity, positivity, finiteness, and endpoint/time-grid conventions. Compare against an independent adaptive solver/tighter tolerance at short duration. Apply the project’s established full-density and scalar-output gates, including absolute and populated-state relative population error.
3. **Validate actual long-duration behavior before changing recommendation/defaults.** Include at least one bounded 200 µs current-build case with both full-density and photon products. If a prior 200 µs reference has exact compatible provenance, reuse it; otherwise use a focused cross-solver/tolerance check for that long case. Choose the remaining 200 µs cases to cover representative detuning and power, plus a Gaussian/enveloped drive case; this is a targeted validation set, not a blanket 4-stage run for every matrix corner. Check the complete trajectory where available and all requested output products. A short convergence result alone does not establish long-time correctness.
4. **Confirm the performance win with paired measurements.** For selected short and 200 µs cases, compare the stable route against `structured` using identical model, initial states, solver, tolerances, time steps, output products, and thread budgets. Measure full density and photons separately and as the application actually requests them. Run at least three alternating accepted pairs for each performance case in the focused validation set, record per-trial resource guards under the current 50% median-CPU ceiling, and report paired spread and medians. Keep preparation, compilation, and solver setup separate from warm solve wall time. Include serial and bounded-parallel baselines; do not promote from RHS-only timing.
5. **Keep promotion decisions explicit.** If every correctness gate passes and paired long-duration results retain a repeatable benefit without unacceptable memory or setup cost, propose changing the RC recommendation to `structured_sparse_dense`. A package/global default change requires a separate review after evidence across the package’s supported workloads; the 11-case matrix alone does not authorize it. If performance is mixed, keep the stable route opt-in and document where it helps. Preserve raw artifacts and all earlier measurements.

## Optional native total-photon adjoint

The prototype result is promising for many initial states at one parameter point, but the comparison must use a fixed total worker budget. Do not require an adjoint to beat an eight-thread direct solve on one point while allowing the direct method eight workers and the adjoint one worker. Instead, compare the complete requested workload—same parameter points, initial states, and photon outputs—with the same total available workers and equivalent hardware allocation. Report both per-point latency and aggregate throughput. Each adjoint solve is parameter-specific; it does not amortize across distinct detuning/power points without another method.

Proceed in separate gates, first implementing the internal opt-in native engine and its correctness tests, then deciding whether to expose a public API and continue to performance validation:

1. **Define the scalar contract and equations.** For the primal `Lρ = −i[H,ρ] + Dρ` and objective `J = ∫Tr(Wρ)dt + Tr(Cρ(T))`, integrate the costate backward using `λ_t = −L†λ − W = −i[H,λ] − D†λ − W`, with terminal condition `λ(T)=C`. The caller supplies `W` using the existing `photon_integral` weight contract; for the RC photon case, weights are `Γ` on B-state populations and `C=0`. Since current Dopri5/Tsit5 solvers require increasing time, use `τ=T−t` and solve `dλ/dτ=L†λ+W`, evaluating `H` at absolute physical time `T−τ`. Reverse the exact segment schedule and carry the costate across boundaries. For decay transfers, preserve the adjoint direction: the forward source-to-target transfer contributes `λ_source += rate * λ_target`. Use the packed Hermitian metric correctly (off-diagonal terms have weight two); return `diag(λ(0))` for basis-diagonal initial states. Do not apply the forward trace-one gate to λ; check finiteness, Hermiticity and duality instead.
2. **Implement the internal Rust engine around existing prepared structures.** Reuse `PreparedLindbladPlan`, parameter graphs/workspaces, source decay rates and incoming transfer lists only for supported structured decay plans. Do not claim general collapse support until the full `C†λC` action is implemented and tested. Keep it out of the forward `LindbladRhs` integral-state augmentation: add a separate adjoint RHS and backward ODE driver. Candidate code areas are `rust/src/lindblad/rhs.rs` (Hamiltonian evaluation and adjoint Hamiltonian/dissipator kernels), `ode_impl.rs` (adjoint ODE RHS), `ode_batch.rs` (reverse segmented solve and parameter-point parallelism), and `python_api.rs` (internal PyO3 entry). Add a Python wrapper/result in `centrex_tlf/lindblad/solve.py`; touch `batch.py` only if needed to match parameter-batch conventions. Add Rust RHS duality tests and Python validation in `tests/lindblad/test_solve.py` / `test_batch.py`. A first version should accept an explicit finite, sorted switch-edge schedule including endpoints; the prepared plan cannot discover every discontinuity. Do not integrate across square-wave edges unsplit. Smooth time dependence may use the existing evaluator. Reject events, state feedback, nonlinear/state-dependent objectives, sampled output and full-density requests. The model and objective weights must be deterministic functions of absolute time and supplied parameters. Reuse work for all requested initial states at one parameter point only; any cross-call cache must include native/model and prepared-plan identity, all scalar overrides, objective weights, span and entry phase, envelope, discontinuity schedule, solver and RHS options. The safe baseline is per-call workspace reuse within one solve.
3. **Prove the native adjoint independently before performance work.** Test Frobenius duality `Tr(λ Lρ)=Tr((L†λ)ρ)` for random Hermitian inputs, complex Hamiltonians, coherent evolution, transfer decay, running weights, exact switch boundaries and absolute-time phase. For the RC model, compare all 70 one-hot photon responses, including zero/near-zero outputs, and a fixed nontrivial diagonal mixture against independent Rust `photon_integral` forward references. Include K=20 as a separately reported workload. Use the pilot photon gate `abs(error) ≤ 1e-6 + 1e-5·|reference|` or a tighter calibrated gate; also require finite, real outputs and nonnegative responses within absolute tolerance. Exercise nominal, detuned and high-power cases, a nonzero entry phase, a switch boundary, and smooth phase modulation at 1, 10 and 200 µs. Compare forward-reference observables to the complete forward density. Do not use trace-one checks on the costate.
4. **Benchmark only after accuracy passes.** Use representative 1, 10 and bounded 200 µs cases, selected detuning/power settings, and at least three paired accepted trials for each claimed performance case. Compare against the fastest validated Rust forward photon kernel (including the promoted sparse–dense kernel), retaining `structured` as a secondary baseline, at 1, 3 and 8 threads under the same total worker budget and with the same parameter grid and initial-state workload. Report per-point latency and aggregate throughput; each adjoint is specific to one parameter point. Separate preparation and first-use costs from warm solves and apply the 50% median-CPU resource ceiling. A near tie within observed timing spread is inconclusive, not a win.
5. **Gate public API readiness on measured throughput.** If all-state accuracy passes and repeated fixed-budget throughput improves materially for a defined workload, expose the explicit scalar photon API. Do not route ordinary photon-output requests to it automatically, present it as a full-density solver, or change defaults. If it does not outperform parallel forward batches at equal resources, keep the public API private/unreleased and retain only the internal experimental engine and its tests.

Combining SoA propagation and the adjoint is not assumed to improve either path: the adjoint has a distinct backward RHS and requires its own kernel design and ablation. A combined implementation can be considered only after each feature independently passes its gates.

## Scope boundary

This plan is limited to the SoA propagation route and the optional total-photon adjoint. It does not authorize implementation or physical benchmarking of response maps, slow modes, restarted/block Krylov, or a production scan. It preserves all historical artifacts, the existing `structured` recommendation, and package defaults until the specified reviews and validation gates are complete.
